What

On most desktops, Control-C gives no sign it worked. This page proposes an enhancement: the operating system flashes what you copied, and shakes when a copy fails.

First, the idea in plain words, then Proposal v0.1, a spec a desktop team can adopt. The demo at the end lets you try it in your browser.

In plain words

When you copy, the thing you copied lights up for a moment and fades. That works for text, a file, an image, or the Copy link button you clicked. Nothing new appears on screen, nothing moves, and it disappears quickly.

When a copy fails, for example because nothing was selected, the element you're working in gives a small shake. If you have the alert sound on, you hear it too.

The system does this, not each app. Once your OS does it, apps can stop showing their own "Copied!" messages. Screen readers keep announcing copies as they do now.

1. Conventions

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 1412 when, and only when, they appear in all capitals, as shown here.

This spec uses these terms.

  • Copy. A user command that puts content on the clipboard without changing what is on screen. It covers keyboard shortcuts, menu items such as "Copy link", and copy buttons.
  • Copied region. The on-screen area that shows the copied content, such as highlighted text, a selected file icon, or the link a "Copy link" item copies. Some copies have none.
  • Trigger. The control or menu item that issued a copy.
  • Failed copy. A copy command that put nothing on the clipboard.
  • Confirmation. Copy feedback saying the copy succeeded.
  • Failure signal. Copy feedback saying the copy failed.
  • Flash. A brief highlight drawn over the copied region, or over the trigger when there is no copied region.
  • Shake. A brief side-to-side movement of the focused element.

2. Confirmation

When a copy succeeds and has a copied region, the system MUST flash the copied region. For a file or an image, the flash MUST cover its bounds, such as the file's icon or the image's frame.

The flash MUST NOT change the selection. What was selected before the copy stays selected after it.

The system MUST flash once per copy. It MUST NOT flash more than three times in any one second, which keeps it within WCAG 2.3.13.

The flash SHOULD strengthen the selection colour and then fade out over about 200 ms.

3. Copies with no copied region

A "Copy link" menu item copies a link that is on screen, so the system MUST flash the link. A copy button often copies content that isn't on screen, so there is no copied region to flash. When a successful copy has no copied region, the system MUST flash the trigger instead.

Some copies have neither, such as a script or a terminal command that writes to the clipboard. For these the system MAY show nothing. A guess at what to flash could point at the wrong thing, so version 0.1 leaves this case open.

4. Failure signal

When a copy fails, the system MUST shake the focused element. If the user has the system alert sound turned on, the system MUST also play it. The shake is the signal you see, and the sound is the one that works when you aren't looking.

The sound is new behaviour. Classic Mac OS never played it on a disabled command. For a disabled menu item, MenuKey returned 0 and did nothing else4.

5. Reduced motion

When the user has turned on the system's reduced motion setting, the flash MUST appear and disappear with no fade. The shake MUST become a static outline around the focused element. The outline MUST look different from the focus indicator, because the element it marks already has focus. The alert sound doesn't change.

6. No preview

The confirmation MUST NOT show the copied content anywhere it wasn't already on screen. The flash marks the copied region in place, so a screen share or a recording shows nothing new.

Android does the opposite. Its overlay previews up to 500 characters of copied text, and closes after 6 seconds56.

7. Ownership

The operating system owns confirmation. On a system that meets this spec, an app SHOULD NOT show its own confirmation, such as a "Copied!" toast, for a copy the system confirms. Two confirmations for one copy tell the user nothing new.

Android 13 set the same rule. Google "strongly recommend[s] removing toasts or snackbars shown after an in-app copy"5.

Screen reader announcements are a separate channel, and this rule doesn't touch them. A screen reader MAY keep announcing copies, because a flash doesn't reach someone who can't see it.

8. Copies made by page code

Section 7 doesn't cover a copy a web page makes through the Clipboard API. The OS sees the write, but not which button caused it. So in this version the page keeps its own confirmation.

The system MUST still flash when it can find a copied region or a trigger for the write. It MUST NOT skip the flash to avoid showing two confirmations.

The Clipboard API asks browsers for no feedback on a write7. A browser flash on the element the user clicked would close this gap, and that change belongs in a W3C filing. Version 0.1 leaves it open.

Isn't this too intrusive?

The strongest objection came from KDE. When someone asked for a copy notification in 2024, Nate Graham said big system notifications for such a common action "would get really annoying". Luis Bocanegra agreed that one "may be too intrusive when you do many copy operations"8. The History page has the full thread.

They're right about notifications. But a flash hides nothing, because it only tints what you copied. It moves nothing, it makes no sound when a copy works, and it's gone in about 200 ms. Nate's own suggestion was an animation, a small shake of the clipboard icon in the tray8. The flash is the same kind of fix, drawn where you're already looking.
