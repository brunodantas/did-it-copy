History

If you press Control-C on most PCs, or Command-C on a Mac, nothing on screen tells you it worked. It's been that way since the mid-1980s. Of all the interface guidelines we read, only one asked for a successful copy to the clipboard to show anything: a 1992 Windows guide made the pointer flash for the pen's Copy gesture21. The earliest systems didn't need a signal, because they kept the clipboard on screen. This page follows how that view disappeared and why nothing replaced it.

Where copy and paste began

Gypsy had no Copy command. You marked the text you wanted, and pressing PASTE at the target made the copy1. The Copy command we know, which fills a clipboard and leaves the original alone, first appears in Apple's Lisa standards in 19804.

  1. 20 April 1975. Larry Tesler and Timothy Mott describe Gypsy at Xerox PARC. It has no Copy key. The user marks a source, shown by a dotted underline, and presses PASTE to copy it to the target1. The 1978 handbook describes the same model2.
  2. September 1979. The manual for Bravo, the Alto editor Gypsy grew from, marks a copy selection with a dotted underline3.
  3. 20 September 1980. The Lisa User Interface Standards define Copy as Cut, "except that the selection is not changed or deleted"4.
  4. 15 April 1981. The Xerox Star spec has a Copy key and no clipboard. Copy "proceeds exactly as with Move, except that a slightly different cursor shape is used"5.
  5. 1983. The Lisa ships with the Clipboard as a desktop object6. LisaWrite's tutorial is the only manual found that has the user watch a copy arrive on the Clipboard7.
  6. 1984. The Macintosh manual teaches Show Clipboard after a Cut. Copy appears only in its reference section8.
  7. 1985. Inside Macintosh says an app "can show" the Clipboard in a window. Copy leaves the selection in the document9.
  8. 1985. The Windows 1.0 user's guide tells users to run CLIPBRD.EXE to see what they copied10.

Tesler wrote in 2012 that "The term copy and paste appears to have originated in Gypsy", and that Gypsy had "dedicated keys for cut, copy, paste, and undo"11. Both Gypsy manuals list only CUT and PASTE, so the keys are UNCONFIRMED. Tesler hedges the first claim himself, and it is UNCONFIRMED too12.

The visible clipboard

The first answer to "did it copy?" was a window: Gypsy and Bravo kept the copied text on screen13. The Lisa put the Clipboard on the desktop, and many owners left it open6. Then the Mac and Windows hid it behind a command, Show Clipboard or CLIPBRD.EXE810. From then on you had to go and look, and nothing took the window's place.

Copy guidelines

Five guides say the user should see the result of an action, yet none applies that to its own Copy entry. IBM's 1989 guide comes closest, since it asks for a message when there's no other visible sign that an action finished, and that describes a copy exactly19. Where the guides do talk about copy, they talk about copy failure. They disable it, dim it, or beep.

Menu hint

Classic Mac OS lit up the Edit menu's title when you pressed Command-C. That part holds to this day92325. But it lit up the title for every Command key, so it told you a shortcut ran, not that you copied. With nothing selected, Copy was disabled, so the title stayed dark and nothing beeped923.

Star's rule

Star shows silence was a choice. It had no clipboard. You pressed COPY, the cursor changed shape, a prompt asked where to put the copy, and the copy arrived there already selected5. Its designers wrote the rule down:

"You never invoke a command or push a key and have nothing visible happen"29

The Star designers, BYTE, April 1982

Why copy got silent

None of our sources says why copy went silent. A copy changes nothing in the document, so by default there's nothing to see. The early systems didn't need a signal because the clipboard was on screen136. When it moved behind a command, nothing replaced it910. Beeps and message boxes were kept for errors1721, and the guides spent their words on the failed copy41719. Each of them had a feedback rule that should have covered copy916192021. None of them applied it.

21st-century feedback

That was the 1980s. Here's what happens today when you copy. We checked each system's docs and, where the code is open, its source.

Android is the only system we checked that confirms an ordinary copy. Since Android 13, every clipboard write brings up an overlay with a preview3032. The rest stay silent for text. At most they confirm special copies, like a screenshot or a copied link, where nothing on screen shows what you copied.

Google now tells Android developers to drop their own "Copied" toast on Android 13 and later, because users would see the message twice30. Once the system confirms a copy, apps don't have to.

Text editors

Web buttons

Pages confirm their own copies because the browser doesn't. The W3C Clipboard API, which pages use to write to the clipboard, says nothing about feedback after a write84. So every site builds its own "Copied!", and each one looks and lasts differently. MDN shows it for 1 second and GOV.UK for 56970.

The KDE objection

KDE's objection is to notifications, and it's fair. A banner after every copy would get in the way. But the KDE HIG also says how to show success, by "visually changing something on the screen related to the task that succeeded"81. A flash on the copied text does that. It obscures nothing, it shows up where you're already looking, and it's gone in about 200 ms.

"it would get really annoying to see big chunky system notifications appearing and covering up content in your windows all the time in response to a very common action"79

Nate Graham, KDE, 24 March 2024
